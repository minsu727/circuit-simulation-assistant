# 00 — Problem Definition & Scope

## 문제 / 목표

LTspice로 회로 실습을 할 때 회로를 생각하는 시간 외에도 반복되는 작업이 많았다. `.ac`, `.tran`, `.dc`의 문법과 입력 순서를 확인하고, waveform을 확대해 값을 측정하고, 소자 값을 바꾸어 다시 실행한 뒤 결과를 비교해야 했다. 보고서에 옮길 수 있도록 결과를 정리하는 일도 남았다.

출발점은 이 반복을 줄이는 것이었다. 앱이 맡을 일을 결정하기 전에 [문제 정의](../../problem-definition.md)를 작성하고, 사용자 입력부터 결과 확인까지의 흐름을 [SPEC v0.1](../../SPEC.md)으로 정리했다.

## 당시 결정

초기에는 자연어로 임의의 schematic을 생성하는 방식도 고려했다. 하지만 current mirror, feedback circuit, 임의의 topology까지 일반화하면 회로 생성 자체가 큰 문제가 된다. 생성된 연결이 의도한 회로인지 검증하는 일까지 v1에 포함해야 하기 때문이다.

그래서 역할을 다음처럼 정했다.

| 역할 | 담당 |
| --- | --- |
| Schematic 작성 | 사용자, LTspice |
| 요청의 구조화와 검토 화면 | 앱 |
| 실행 조건의 최종 승인 | 사용자 |
| Simulation | LTspice |
| RAW 기반 정량 분석 | Python |
| 결과 해석과 최종 설계 판단 | 향후 AI 보조, 최종 판단은 사용자 |

이 범위에서는 사용자가 이미 작성한 회로를 기준으로 입력·실행·측정의 연결을 검증할 수 있다. 회로 생성은 장기 확장으로 남기고, 먼저 완성 여부를 확인할 수 있는 단위로 제품 범위를 줄였다.

## 구현

이 단계의 산출물은 앱 기능보다 개발 계약에 가까웠다. SPEC에 **요청 → 조건 구조화 → 검토·수정 → 승인 → 실행 → 측정** 순서와 승인 전 실행 금지를 명시했다. Gain이나 bandwidth 같은 숫자는 Python으로 계산하고, 해석과 측정 사실을 분리하기로 했다.

First Milestone도 화면과 실제 실행 연결부터 시작하도록 나눴다. 사람이 범위·승인 경계·완성 기준을 정하고, 그 범위를 담은 prompt로 Codex에 구현을 요청한 뒤 검증하는 방식이다. 이후 단계의 실제 LTspice 검증과 사용자 테스트도 이 기준 위에 추가됐다.

SPEC에는 AI 자연어 이해, 여러 분석 종류, 보고서 등 장기 목표도 들어 있다. 이를 당시 구현 완료 목록으로 읽어서는 안 된다. 현재 요청 parser는 rule-based이고, 보고서와 임의 회로 생성은 구현하지 않았다.

## 검증

2026-09-14의 원본 계획 기록에는 문제 정의, scope 결정, SPEC 작성과 First Milestone이 남아 있다. 이 단계에 unit test 수나 실제 LTspice 실행 결과를 붙이지 않는다. 측정 가능한 시간 절감 효과를 입증한 기록도 없다.

## 실패 / 문제

당시 기록의 핵심 문제는 실행 오류가 아니라 범위였다. 자연어 입력이라는 공통점만으로 회로 생성과 simulation 보조를 함께 구현하면, 어느 부분의 성공을 먼저 검증해야 하는지 불명확해진다.

## 수정 / 배운 점

Schematic을 입력으로 고정하자 원본 보존, 승인 차단, RAW 생성, 계산 정확성처럼 확인할 항목이 구체화됐다. 이후 prompt에서 새 기능을 제한하고 회귀 검증을 요구할 수 있었던 기준도 이 결정이었다.
